# 《软件工程—敏捷 DevOps 方法》课程要求与 GitHub 证据映射

**来源**：教师提供的《大作业 V1.1》；老师已同意以 GitHub 替换华为平台，但**没有取消个人博客题目**。评分按教师文档原表整理（不是对评分的重新解释）。

## 最终成绩三部分

- 开发全过程完成度：**60%**
- 开发过程总结描述：**25%**
- 对软件开发过程的思考和建议：**15%**

## 60% 工程阶段细项（11 项）

| 项目 | 比重 | GitHub 路线建议提供的真实验收证据 | 何时做 |
|---|---:|---|---|
| 项目规划 | 5% | PRD、工作分解、GitHub Projects Roadmap | 阶段 0 开始 |
| 工作项设置 | 5% | Epic/Feature/Story 到 Issue/子 Issue，优先级、负责人、验收标准 | 阶段 0 起 |
| 迭代 | 5% | Projects Iteration、迭代计划与实际完成记录 | 阶段 0 起 |
| 开发提交 | 5% | 真实 Git commit、feature 分支 | 每轮 |
| 代码检查 | 5% | ESLint 等检查结果、Review 评论 | 阶段 0 起 |
| 构建配置 | 6% | 可重复构建命令和产物；Actions 构建日志 | 阶段 0 起 |
| 持续集成 | 5% | PR/push 自动运行的 Actions（非手动伪造截图） | 阶段 0 起 |
| 主机配置 | 6% | 后续选择的真实可验收运行环境配置、网络与安全设置 | 后续部署前 |
| 部署配置 | 8% | 后续真实发布流水线与访问验证 | 后续部署 |
| 分支合并 | 5% | PR、团队互审、合并记录、检查要求 | 每轮 |
| 持续交付流水线 | 5% | 自动交付、发布门禁及部署记录 | 后续部署 |

**开发任务要求**：个人博客至少涉及登录、文章发表、评论功能；需要总结过程、反思与改进建议。星空、羽毛信是产品特色，但不能取代真实功能和 DevOps 证据。

**注意**：老师确认的是工具链替换；具体将 Vercel 等全托管平台视为“主机配置”的等价验收，尚无明确确认。阶段 0 不购置主机或锁定部署服务。

**不要制造假的敏捷历史**：Issues、里程碑、PR、审查与 CI 需从实际开发时留下；不能临近验收再回填虚假过程。
